2. 这次应如何评估

先看结果，再看拼装。实际 cache_read_tokens 和 cache_hit_ratio 是“是否命中”的唯一结果证据；context 拼装、哈希和相邻 diff 是“为什么命中或失效”的解释证据。两者不能互相替代。

  • 连续调用不是天然可缓存。只有请求起始 token 序列保持一致，才可能复用已缓存前缀。
  • 把静态系统指令、固定工具定义放最前面；把用户当轮输入、动态计划、工具结果和时间戳放后面。
  • 模型、实际部署/路由和 cache key 是分段键。切换其中任一项，应作为预期冷启动而非拼装失败。
  • 系统和 tools hash 相同不足以证明可命中；历史消息若被截断、重排、压缩或改写，首个差异位置之前以后的缓存会失去价值。
官方规则的应用边界：本报告以 OpenAI Prompt Caching 指南所述的自动前缀缓存、稳定前缀和 cache key 分路由原则作评价框架。由于本次官方文档检索网关不可用，未将网页抓取结果作为额外证据；数值均直接来自本地 trace 的 response_usage。

5. 根因优先级与改造建议

P0：把“实际出站请求”作为唯一拼装真相

  • 在发送 API 前生成 canonical request fingerprint：model/deployment、prompt_cache_key、system、tools、messages 的确定性序列化哈希。
  • 记录 token 级或分块级前缀 hash，并标记第一个 token/消息差异，而不仅是总 message SHA。
  • 动态字段不得混入稳定 system 区：时间、plan、subagent 状态、runner hint、请求 ID 均应放到动态尾部或从 prompt 移除。

P1：禁止历史消息的反复重写

  • 工具结果截断/压缩使用一次性、确定性、幂等的规范化；相同输入必须产生字节级相同输出。
  • 不要为新一轮请求重排、重包装或重新格式化已存在的 history。新增内容只追加到尾部。
  • 把分支、摘要切换、模型切换显式标成新 episode；不要把它们当作同一条连续缓存链路。

P2：补足观测字段，区分“拼装问题”和“提供方未复用”

  • 每条 trace 增加：prompt_cache_key、实际 endpoint、模型 deployment/路由、请求时间、缓存阈值是否满足、response id 和原始 usage。
  • 低命中自动分类：预期冷启动、system/tool 变化、首消息前缀断裂、历史改写、长前缀仍未命中、不可判定。
  • 65 条缺 previous_run_id 的连续对必须标为不可判定，不得计入拼装失败率。

7. 最终判断

应当“两层评估”：第一层用 provider 返回的 cache_read_tokens/cache_hit_ratio 判定好坏；第二层针对低命中，分析实际 context 拼装后的稳定前缀、工具定义、历史消息与 cache key。就这份 trace 而言，系统和工具稳定不是主要矛盾；历史消息前缀断裂、跨模型/路由混合以及观测缺口才是主因。
