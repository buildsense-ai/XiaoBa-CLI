# 业务资料类型与整理线索

首次整理一批业务资料或出现陌生类型时参考；普通查询或同批后续更新无需反复加载。下表是可扩展的判断示例，不是必填表单或封闭分类表。字段只保留原资料实际提供且与任务相关的内容；缺项影响使用时注明，不能为了填满模板推断事实。

## 怎样选分类和组织内容

- 先看内容的业务用途和用户以后会问什么。所属对象、资料类型、状态/时间是不同维度：同一客户可以有订单、发票、会议记录；同一PDF也可以混合这些资料。同名、相近金额或相近日期不足以证明对象或记录相同。
- `category` 只接收一个主分类，优先复用当前知识库中含义一致的分类。下表英文名是建议，不要求重分类旧知识，也不将所有业务资料笼统归为 `projects`。自定义名须符合 `[a-z][a-z0-9-]{0,49}`；对象、子类型、日期等放入现有标题、summary和Markdown正文，不发送 `customer_id`、`document_type`、`tags` 等新增JSON字段。
- 混合资料可以按主题分节；独立更新、适用范围不同或超过文件限制时分篇，用真实业务编号和KB-ID/章节关联。索引或对象概览指向明细，避免为每个维度重复保存同一份可变事实。分类只是检索线索，不构成公司/客户之间的访问权限隔离。
- 新类型自行判断其主要用途，保留稳定标识、必要明细、适用范围及来源。暂时无法归类时可用 `reference` 并写清资料实际内容；只有歧义会影响事实关联、处理范围或结论时才询问用户。不能只因类型未列出就跳过资料。
- 即使类型已在表中，判断示例或现有分类不贴合资料时，也可以采用更准确的自定义分类；用户明确指定的分类优先。正文用简短“资料类型/分类说明”写清名称和含义，例如“资料类型：设备校准记录；记录测量偏差、校准条件及结果”。修正旧分类时在change写明原因，沿用原KB-ID并保留有效事实和来源；不为更换分类另建重复知识，也不批量改动无关资料。

## 常见类型及保留重点

每类均遵循主Skill的来源短引用、事实与推断区分、核验和更新规则。下列重点帮助选择组织方式，不替代用户明确要求的保存范围。

| 类型与建议category | 常见资料；组织和核对重点 |
| --- | --- |
| 客户、公司、供应商等对象 `entities` | 客户表、合作方档案、联系人名单；来源编号、准确名称/别名、联系人所属关系与有效日期。客户、供应商是业务角色，不能仅凭同名合并公司或个人；概览关联订单等明细。 |
| 销售与商机 `sales` | 线索、跟进记录、报价、投标材料；客户/商机/报价编号、需求、阶段、报价版本/有效期、承诺及条件。意向、报价、确认订单分别记录，不将预计收入当已成交。 |
| 合同与协议 `contracts` | 合同、补充协议、服务约定；签约方、编号、签署/生效/到期日、义务、验收/付款条件及例外。草案、已签和已履约区分，补充条款注明替代范围及生效时间。 |
| 订单、采购与交付 `orders` | 销售/采购订单、收货、送货、验收单；订单与行号、关联对象、商品、数量/单位、价格、交期、部分交付/取消状态。下单、出货、收货、验收分别记录，不能自动互相推定。 |
| 财务、票据与对账 `finance` | 发票、收付款、退款、报销、预算、对账单；各自编号及关联、金额/币种/税额口径、日期、有效/作废/红冲状态。开票不代表收款，预算不代表实际发生；一单多票、多笔收款保留对应明细，合计按完整范围精确计算。 |
| 产品、服务与定价 `products` | 产品目录、规格、服务套餐、价目表；SKU/型号/版本、参数与单位、兼容性、价格适用客户/区域/期限、含税及优惠条件。旧价与现价、选配与标配、计划与已发布能力区分。 |
| 项目与交付管理 `projects` | 需求、计划、里程碑、任务、交付报告；项目/需求编号、负责人、依赖、目标、进度、验收标准、变更范围。计划完成与实际完成、待验收与已验收分别记录。 |
| 操作手册与培训 `procedures` | SOP、安装/使用说明、培训讲义；适用角色/产品/版本、前提、步骤顺序、输入输出、异常分支与完成判据。FAQ保留问题与适用条件；不能从另一版本补入步骤。 |
| 制度、规则与审批 `policies` | 内部制度、审批矩阵、规范条款；发布方、版本、适用对象/地域、生效期、规则、例外、审批角色和条款号。建议、内部规则和外部要求标清来源性质，不擅自扩大适用范围。 |
| 人事与组织 `people` | 组织架构、岗位职责、招聘、入离职、考勤、培训记录；人员/岗位编号、组织关系、事件日期及状态。计划入职不等于已入职，个人评价保留评价者和语境；只整理任务需要且获准保存的信息。 |
| 客服、故障与复盘 `troubleshooting` | 工单、投诉、事故、排障记录；对象/版本、症状、时间线、复现条件、证据、排查动作及结果。假设原因、确认原因、临时措施与验证过的修复分开，恢复时间与关闭工单时间不混用。 |
| 技术环境与接口 `environment` | 部署配置说明、架构、API文档、迁移说明；组件/接口/环境/版本、依赖、参数单位、约束、已验证命令和变更日期。文档声明与实际观察区分；密钥仅记录原配置位置和用途。 |
| 库存、物流与资产 `operations` | 出入库、库存快照、运单、设备台账、维修记录；SKU/批次/序列号、仓库/位置、数量单位、移动时间、责任方。库存余额与流转记录、在途与已签收区分，不能把多个时点快照相加。 |
| 会议、沟通与决策 `decisions` | 会议纪要、邮件、聊天、访谈；参与者、日期、主题、已确认决定、行动项/负责人/期限、待定分歧及原话定位。提议不等于批准；转述、个人意见与正式约定分开，不把全部聊天流水变成确定知识。 |
| 研究、统计与数据集 `research` | 调研、问卷、实验记录、统计表、分析报告；问题、样本/覆盖范围、数据版本、字段定义/单位、方法/筛选口径、时间区间、结论及限制。观察与因果推断分开，空值不默认为零，预测不当实际值。 |
| 内容、营销与设计素材 `content` | 活动方案、文案、案例、图稿、音视频转录；目标受众/渠道、主题、版本、审批/发布状态、活动期限和原素材定位。正文与文案建议区分，图表保留图例/坐标单位，音视频用页帧或时间段定位；未知授权不推定可复用。 |

行业专门资料可按业务用途延伸，如质检记录、工程图纸、课程、设备检测报告：保留其原有术语、编号、单位、版本及判定依据。分类信心不足不代表原文事实无效；可先用准确标题和中性描述保存，再在获得资料后修正分类。

## 混合资料示例

某公司的Excel含客户表、订单表、收款表，另附合同PDF与安装手册：以来源中的客户/订单编号关联；对象概览归 `entities`，订单明细归 `orders`，收款与发票可在 `finance` 下分节，合同归 `contracts`，手册归 `procedures` 并注明适用产品/版本。这个示例不要求一定建五篇；按实际记录量、更新方式及已有KB决定合并或拆分。跨篇只保存必要关联与检索入口，不复制全部客户档案到每张发票。

## 编写参考

以下来源用于启发资料范围和组织重点；上面的category与整理方法是本Skill的应用设计，不是这些来源规定的统一分类标准。使用本参考无需联网，也不引入来源中的保管期限或业务规则。

- [NARA GRS Coverage](https://www.archives.gov/records-mgmt/grs/grs-coverage)：财务、人事、IT、设施、客服等常见职能资料覆盖范围。
- [Schema.org Invoice](https://schema.org/Invoice)：账单与客户、订单、日期、金额及支付状态的关联线索；具体票据语义仍以原资料为准。
- [Schema.org TechArticle](https://schema.org/TechArticle)：技术说明、操作指引和故障排查等资料类型。
- [W3C DCAT 3](https://www.w3.org/TR/vocab-dcat-3/)：数据集描述、时空覆盖、版本和相关资源的组织参考。
